## 三、方法论：这次是怎么查的

刻意采用「**多人独立 + 交叉戳**」的结构，而不是一个人自查自改：

| 阶段 | 承担者 | 产出 |
|---|---|---|
| 后端对抗性审计 | 工程师（寇豆码） | 37 项发现，28 项修复 |
| 前端对抗性审计 | 工程师（寇豆码） | 31 项发现，24 项修复；e2e 补 1 项 |
| 独立回归验证 | QA（严过关） | 逐条实测 + 53 条新测试 + 8 项残留风险 + 2 条加固建议 |
| 小程序端审计 + 加固落实 | 工程师（寇豆码） | 9 项发现，9 项修复；落实 2 条加固建议 |

**四个关键纪律**，也是这次能挖出东西的原因：

1. **不只查「代码看起来对不对」，而是实测**。例如「解压炸弹是否在解码前被拦下」这条，QA 用 `monkeypatch` 给 `ImageFile.load` 打计数器，实测请求结束计数为 **0**，才敢确认「未解码就拦下」——光看代码只能看到「有个像素上限校验」，看不出它到底在校验前还是校验后。
2. **修复者与验证者分离**。工程师报「e2e 已实跑 3/3 通过」后，QA 仍独立起服务重跑了一遍，并额外发现工程师第一版 e2e 有「永远 skip」的假绿问题。
3. **鼓励推翻前序结论**。工程师第一轮判断「本机没有 Playwright 浏览器」，第三轮自己更正为**判断错误**（按 Linux 路径找的，Windows 实际在 `AppData\Local\ms-playwright`），并把 e2e 真跑通了。
4. **验证阶段"要求"与"实测"分开记账**。QA 提的 2 条加固建议（测试限流隔离、只读端点补限流）单独列出并落实，不混进"已发现缺陷"的数字里充数。

### B-01 【P0】DeepSeek API Key 明文硬编码

**位置**：`apps/server/config.json:2`（原）→ `main.py:48-119`（改）

**现象/风险**：真实付费 Key 以明文躺在源码目录。项目**不是 git 仓库**（无 `.git`），尚未被推送到远端，但只要目录被拷贝/备份/发给别人就泄露，任何人拿到即可刷爆额度。

**根因**：`os.environ.get(...) or CONFIG.get("api_key", "")` —— 把配置文件当成密钥的一等来源。

API_KEY = os.environ.get("DEEPSEEK_API_KEY") or CONFIG.get("api_key", "")

```python
# 修复后
API_KEY = (os.environ.get("DEEPSEEK_API_KEY") or "").strip()
...
if not API_KEY:
    logger.warning(
        "未设置环境变量 DEEPSEEK_API_KEY，识别接口将直接报错。"
        "启动前请先配置，例如：set DEEPSEEK_API_KEY=sk-xxxxxxxx")
```

同时：`config.json` 里的 `api_key` 整条删除、新增 `config.example.json` 模板、启动阶段对残留 `api_key` 一律忽略并告警。

### B-02 【P0】令牌签名密钥明文 + 自动回写 config.json

**位置**：`main.py:58-67`

**根因**：把「持久化随机密钥」当成默认行为。三重后果：
1. 多实例/容器部署时每个实例生成不同密钥 → 用户令牌随机失效（表现为「莫名其妙被踢下线」）；
2. 只读文件系统（容器 `readOnlyRootFilesystem`）上 `os.replace` 直接抛异常 → **服务起不来**；
3. 写回的是整个 CONFIG，并发或崩溃可能截断文件。

```python
# 修复前
SECRET = CONFIG.get("secret", "")
if not SECRET:
    SECRET = secrets.token_hex(32)
    CONFIG["secret"] = SECRET
    _tmp = CONFIG_PATH.with_suffix(".tmp")
    _tmp.write_text(json.dumps(CONFIG, ensure_ascii=False, indent=2), encoding="utf-8")
    os.replace(_tmp, CONFIG_PATH)
```

```python
# 修复后
SECRET = (os.environ.get("BOOKFINDER_SECRET") or "").strip()
if not SECRET:
    SECRET = secrets.token_hex(32)
    logger.warning(
        "未设置环境变量 BOOKFINDER_SECRET，已生成临时进程内令牌密钥；"
        "服务重启后所有用户需重新登录。生产环境请固定该环境变量。")
```

**降级行为明确**（重启后需重新登录），不是静默失败，也不再因写盘失败而崩溃。

### B-07 【P1】SSE 识别流：断连不收工 + 队头阻塞 + 无界队列

**位置**：`main.py:167-231`

**三个独立问题**：
1. `queue.Queue()` 无界且 `put` 永不阻塞 → 客户端中途断开后生成器被关闭，但**工作线程完全感知不到**，继续把结果塞进队列并继续调付费 API；
2. `pool.map` 按提交顺序产出 → 第 1 块慢（重试 3 次 ×300s）会把第 2~16 块已完成的结果全部堵住，用户看到进度条长期停在 0；
3. 生成器被 GC 时没有任何通知机制。

```python
# 修复前
events: queue.Queue = queue.Queue()
...
with ThreadPoolExecutor(max_workers=4) as pool:
    for res in pool.map(work, tiles):
        events.put(res)
```

```python
# 修复后
events: queue.Queue = queue.Queue(maxsize=max(8, len(tiles)))
stop = threading.Event()

def _put(item):
    while not stop.is_set():                 # 断开后不再死等
        try:
            events.put(item, timeout=0.5)
            return
        except queue.Full:
            continue

def run_all():
    pool = ThreadPoolExecutor(max_workers=4)
    try:
        futs = [pool.submit(work, t) for t in tiles]
        for fut in as_completed(futs):       # 谁先好推谁，消除队头阻塞
            if stop.is_set():
                break
            if fut.cancelled():
                continue
            _put(fut.result())
    finally:
        pool.shutdown(wait=False, cancel_futures=True)  # 取消未开始的切块
        _put(None)
...
try:
    while True:
        ...
finally:
    stop.set()          # 生成器被关闭（客户端断开/GC）时通知工作线程收工
```

**验证**：QA 用 sleep 0.5s 的假视觉接口，连续 3 次「取 2 个事件后立刻 `gen.close()`」模拟断开，10 秒内 `ThreadPoolExecutor` 线程数**回到基线**；既有的 meta/done 事件契约未变（原有 SSE 断言用例全过）。

  const resp = await fetch("/api/recognize", {

## 八、残留风险清单（改完之后仍然存在）

**这一章比问题清单更重要**——以下 8 项是本次修复**没有解决也无法在本次解决**的风险，需要你知情。

| # | 风险 | 说明与建议 |
|---|---|---|
| 1 | **限流是内存级、单进程** | `uvicorn --workers 4` 时实际阈值变成 4×60；进程重启即清零。根治需 nginx 限流或 Redis |
| 2 | **`_client_ip` 不读 `X-Forwarded-For`** | 这是防伪造的正确选择，但一旦部署在 nginx 后，**所有真实用户共享同一个 60/min 注册桶**，NAT/办公网出口下会误伤正常用户。**上线前必须明确部署形态** |
| 3 | **`BOOKFINDER_SECRET` 未设置时的降级** | 多 worker 下 A 签发的令牌到 B 就验签失败 → 用户随机掉线。代码已有告警，但需运维约束 |
| 4 | **`_my_records()` 全量扫盘**（限流已补，**根因仍在**） | 代价随**全局**记录数线性增长（与调用者无关）。验证阶段已给 `/api/results` 等 4 个端点补上限流（V-02），但记录上万后仍会明显退化。根治需引入 SQLite 元数据索引或改存储结构 |
| 5 | **`?token=` 令牌仍在 URL 上** | 暴露面已收敛到 `/results/`，但未消除。根治需改为**短时效签名 URL**（服务器签一个 5 分钟有效的 HMAC token 给图片路由），需前后端 + 小程序同时改 |
| 6 | **解压炸弹只防了像素维度** | 30MB + 5000 万像素两道闸都过后，仍会有一次真实的 4800 万像素解码（约 144MB/请求）。并发几路就能把内存打高，硬防需限制并发或按可用内存动态调阈值 |
| 7 | **限流无「惩罚/黑名单」** | 攻击者可稳定地每分钟打满 60 次注册，只是慢，不会被阻断 |
| 8 | **`Image.MAX_IMAGE_PIXELS` 是全局赋值** | 任何后续代码（或依赖库）改了这个全局值，门禁就失效，没有别处兜底 |
| 9 | **小程序端无运行时验证** | 9 项修复只过了静态检查（语法 + JSON + setData 字段名核对），未在真机/模拟器跑过（本机无微信开发者工具 CLI） |

### 8.1 已接受的风险（明确决定不改，附理由）

| 项 | 决定 | 理由 |
|---|---|---|
| 注册接口 409「用户名已存在」= 用户枚举 | **保留** | 前端收敛文案会牺牲「这个名字被占了」的可用性；且已由 60/min/IP 限流大幅缓解。若将来对外开放，再改为统一文案 |
| token 存 localStorage（XSS 可盗） | **保留（需后端配合才能根治）** | 根治要改 httpOnly + Secure Cookie 并加 CSRF 防护，属鉴权链路重构。当前无 `innerHTML` 注入面 |
| 从 `config.json` 读 `wechat_appid` | **保留** | AppID 不算密钥，公开无风险 |
| `results/` 目录无清理/配额策略 | **待你决策** | 每次识别永久落一张 `image.jpg`，磁盘会无限增长。需要产品决策（保留 N 天 / 总容量上限） |
| 前端列表无虚拟滚动 | **保留** | 需引入 `@tanstack/react-virtual` 等新依赖，违反本轮「不引入新依赖」约束 |

## 十、常见坑记录（给后续维护者）

这次审计踩到/确认的本机与框架坑，值得留档：

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | `pytest --basetemp` 指向已存在目录 → safe-delete 钩子拦截 → 假性 36 errors | 每次用一个**不存在**的新目录 |
| 2 | 项目 venv 缺 pip 且缺 `httpx2` → `fastapi.testclient` RuntimeError，55 个 API 用例根本无法运行 | `python -m ensurepip --upgrade` + 装 `httpx2` |
| 3 | `pnpm exec tsc` 间歇性报「不是内部或外部命令」 | 用 `node ./node_modules/typescript/lib/tsc.js -b --force` |
| 4 | vite 默认只监听 `::1`，`127.0.0.1:5173` 连不上 | 加 `--host 127.0.0.1` |
| 5 | Playwright 浏览器在 Windows 的 `AppData\Local\ms-playwright`，不在 `~/.cache` | 别按 Linux 路径找，也别急着重下 |
| 6 | 8000 端口被**同项目 v2 版本**的残留 uvicorn 占着 | 起服务前先确认端口归属 |
| 7 | `openpyxl` 读回空字符串单元格返回 `None` 而非 `""` | 断言时按 `None` 处理 |
| 8 | Python `json.loads` 默认接受 `NaN`/`Infinity`，但 JS `JSON.parse` 不接受 | 跨语言 JSON 边界必须显式过滤 |
| 9 | `navigator.mediaDevices?.gUM(...).then(...)` 可选链会短路成 `undefined` 而非跳过整链 | 必须显式判空 |
| 10 | `crypto.randomUUID` 在 http 局域网访问下为 `undefined` | 必须做降级实现 |
| 11 | 本机 bash 缺 coreutils（`ls`/`head`/`tail`/`find` 均 not found） | 命令不要接管道给 tail/head，输出重定向到文件再读 |
| 12 | **同一文件的多处修改若在同一批里并发下发，只有一处会落盘** | 逐条改、逐条 Read 复核落盘结果 |
| 13 | 限流状态是**进程级全局**，测试间会互相污染 | 用 autouse fixture 前后双清（V-01 已落地） |
| 14 | 新增测试用例会让既有用例的限流"余量"变小，表现为数周后突然随机 429 | 见坑 13；根因是共享全局状态而非"偶发" |
